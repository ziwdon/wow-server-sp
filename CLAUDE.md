# CLAUDE.md

Guidance for Claude Code (claude.ai/code) working in this repository.

## What this repo is

Two sibling sub-projects on Docker:

- **`scripts/`** — single-file bash installer for AzerothCore (WoW 3.3.5a) + mod-playerbots + mod-ah-bot-plus + mod-individual-progression. AC stack installs under `/opt/stacks/azerothcore/`.
- **`wow-server-sp-admin/`** — FastAPI + HTMX web admin for monitoring/editing the running AC server. Installs to `/opt/stacks/azerothcore-admin/` (separate stack dir so its lifecycle never disturbs AC's). Every config edit becomes an `AC_*` env var in `docker-compose.admin.yml`, the LAST-precedence Compose layer. Use the current implementation and its tests as the authoritative behavior.

**Target environment:** Ubuntu 22.04 LTS (recommended; 24.04 allowed only after explicit user confirmation — "possible, maybe", not supported). Ryzen 5 7430U, 16 GB RAM, 512 GB SSD. Tailscale required for remote WoW clients (no public IP / port forwarding); LAN clients may optionally connect directly via the installer's LAN IP prompt (see *Optional direct-LAN play*). Use case: ~2 humans + a few hundred playerbots.

## Mandatory live-stack test safety

The following rules were added after the 2026-07-13 incident in which a direct
Compose-style teardown removed the live AzerothCore containers and default
network. The persistent database data survived, but the service was unavailable.
Docker logs did not preserve the initiating process, so do not claim a specific
actor without evidence. A test isolation path was found that could call host
Docker; this guard prevents that class of failure.

`/opt/stacks/azerothcore`, `/opt/stacks/azerothcore-admin`, the local Docker
daemon/socket, `azerothcore.service`, and all `ac-*` / `azerothcore-*`
containers, networks, and volumes are live production state. Only perform a
live lifecycle operation when the user has explicitly requested it.

When testing an installer, uninstaller, backup/restore path, or any script that
can remove, stop, restart, or reconfigure services:

- Never let the test reach the host Docker daemon or `/opt/stacks`. It must not
  invoke real `docker compose down`, `docker rm`, `docker network rm`, `docker
  volume rm`, `sudo`, `systemctl`, destructive `rm`, or `crontab` operations;
  `--yes` does not make a host-side test acceptable.
- Copy the script into a temporary sandbox and isolate or rewrite every
  hard-coded live path. Passing environment overrides alone is insufficient:
  inspect the script to prove it uses them.
- Use a stub-only `PATH` for `docker`, `sudo`, `systemctl`, `rm`, and `crontab`,
  or a sandboxed VM/container with no `/var/run/docker.sock`, no privileged
  access, and no host `/opt` mount. A destructive test must fail closed if any
  of those protections is absent.
- Before execution, explicitly confirm the target canonicalizes outside
  `/opt/stacks`, each dangerous command resolves to its test stub, and no host
  Docker socket/daemon is accessible. Exercise `--dry-run` first whenever it
  exists.
- After every lifecycle-related test or attempted command, run a non-mutating
  live health check. If an expected AC or admin container is down, stop all
  testing and report it. Do not restart, restore, redeploy, or otherwise change
  the live service without explicit user direction.

## Architecture

**`scripts/install-azerothcore.sh`** — the core of this repo:
- `set -euo pipefail` + `trap on_error ERR` that prints phase/line and the resume command
- Phase checkpointing: state in `~/.azerothcore-install-state`; the `PHASES` array defines order and drives `--resume-from` index comparisons
- Config captured up front via prompts; persisted to `~/.azerothcore-install-config` (mode 600), sourced on resume, shredded on success
- Three manual pauses: Tailscale auth, GM/AHBOT account creation via `docker attach ac-worldserver`, AH bot character creation in the WoW client
- Logging starts at `/tmp/azerothcore-install-<ts>.log`, relocated to `logs/` once it exists; `exec > >(tee ...)` preserves original stdout/stderr for `clean_exit`

**`scripts/verify-azerothcore.sh`** — `set -u` (not `-e`) so every check runs after a failure. Reports `[OK]`/`[FAIL]`/`[INFO]` per check; INFO is advisory, excluded from pass/fail totals.

**`scripts/redeploy-azerothcore.sh`** — isolated graceful recompile + redeploy of only `ac-worldserver` after a source/module edit: `docker compose build ac-worldserver` (ccache-fast) → graceful stop (clean saveall) → recreate. Never touches `.env`/`override.yml`/`admin.yml`/the DBs. Use this instead of `install-azerothcore.sh --resume-from=3`, which would also run Phase 4 DB-init, the account-creation pauses, networking, etc. **It is not an upgrade tool**: it rebuilds only the worldserver image, while a real upstream bump rebuilds all four and runs the new `ac-db-import` first (see *Pinned upstream + upgrades*). Readiness polls `docker logs --since "$StartedAt" ac-worldserver` for `World Initialized` (current-container evidence via `docker inspect -f '{{.State.StartedAt}}'`) — not the host-mounted `Server.log`, which isn't guaranteed truncated by the time polling starts. `restore-azerothcore.sh` uses the same current-boot-evidence pattern.

**`scripts/uninstall-azerothcore.sh`** — `docker compose -p azerothcore down` + explicit named-container cleanup; never `--remove-orphans` (see Constraints).

**`clean_exit` vs `exit`:** `clean_exit` disarms the `ERR` trap — use it for graceful aborts (e.g. user-must-act-and-rerun) so no error banner prints. Plain `exit` or a failing command prints the banner via `on_error`.

**`skills/wow-server-sp-gamemaster/`** — the Game Master skill. Source lives here; copy to `~/.claude/skills/wow-server-sp-gamemaster/` to install globally. Invoke via the `Skill` tool (auto-triggers on questions about install, GM commands, playerbots, AH bot, individual progression, admin app, troubleshooting). `SKILL.md` routes each topic to one of 15 `references/` files (install phases, client setup, GM commands, worldserver.conf/`AC_*` env vars, playerbot commands + raid strategies, AH bot, progression tiers, admin app, troubleshooting, SQL queries).

## Install phases

From the `PHASES` array in `install-azerothcore.sh`:

`0.0` pre-flight → `0.1` OS check → `0.2` apt → `0.3` Docker → `0.4` Tailscale → `0.5` dirs → `1` git clone + pin to `upstream-versions.env` + local patches (core + 3 mods) → `2.1–2.6` config/compose → `3` Docker build → `3.1` module conf templates → `4` first run + DB init → `pause-2` account creation → `5` realmlist → `5.1` UFW → `pause-3` AH bot chars → `6.1.4` write GUIDs → `6.1.5` worldserver restart → `7` backup cron → `8` systemd

There is no `pause-1`: the first manual pause (Tailscale auth) runs inline in phase `0.4`; only pauses 2 and 3 are standalone phases.

## Pinned upstream + upgrades

**`scripts/upstream-versions.env` is the only source of upstream revisions.** Per repo: URL, branch, full 40-char SHA (core = `mod-playerbots/azerothcore-wotlk` `Playerbot`, plus the three modules) and `CLIENT_DATA_VERSION`. `scripts/lib/upstream-versions.sh` *parses* it, never sources it (whitelisted keys, shell-safe values, SHAs must be 40 hex) and provides `upstream_repo_specs` (`label|dir|url|branch|rev`, core first) and `checkout_pinned_rev` (init if needed, `fetch --depth 1 origin REV` only when the commit is absent, `checkout -B BRANCH REV`, assert HEAD; git itself refuses to overwrite local edits to tracked files). Three consumers: installer Phase 1 (`pin_upstream_checkouts`, `install-azerothcore.sh:1209`, called after the clones at `:2665`), verifier Checks 24/26, and `upgrade-azerothcore.sh`. Change the file only through the upgrade script.

Live server cut over to these pins on 2026-10-27; rollback available until `finalize`.

**Never re-run the installer from Phase 1 or earlier (`--resume-from`/`--force-from` <= 1) against a live stack that is not already at the pins.** Phase 1 now pins, i.e. `checkout -B`s the core tree and the host-mounted `./modules` checkouts under the running containers. The worldserver applies mod-playerbots' DB-update SQL from that host mount (spec U-5), so moving it while the old worldserver can restart runs new SQL against the old binary (e.g. it drops `playerbots_speech`, which the old binary still prepares, then aborts). Resuming from Phase >= 2 is unaffected. Live upstream changes go only through `upgrade-azerothcore.sh`, which builds in a separate staging checkout.

**Local patches: `scripts/patches/<module>/*.patch`, applied by `apply-local-patches.sh SOURCE_ROOT [--check|--reverse]`** to `SOURCE_ROOT/modules/<module>`, in filename order. Idempotent: an already-applied patch is kept; one that neither applies nor reverse-applies exits 1 ("refresh the patch for this upstream revision"); `--check` exits 1 if any is not applied; `--reverse` un-applies newest first. Phase 1 runs it right after pinning; Check 24 runs `--check`. `0001-mark-only-logging-out-character-offline.patch` (mod-playerbots `src/Script/Playerbots.cpp`) implements `OnPlayerCanMarkAccountOffline` (hook `PLAYERHOOK_CAN_MARK_ACCOUNT_OFFLINE`): it runs `UPDATE characters SET online = 0 WHERE guid = …` and returns false. Why (spec U-3, DEC-1): core `3f2969dd` logout runs `CHAR_UPD_ACCOUNT_ONLINE`, marking **every** character of the account offline, and the pinned mod-playerbots no longer overrides it; a playerbots account routinely has several characters in the world (random bots, alt bots on the human's account), so dismissing one alt-bot would flag the human offline for up to 15 min and break the presence tracker, Players page and online counts. A new upstream revision may force a patch refresh (hunk context); never loosen the check to get past "neither applies".

**Pre-db-import SQL: `scripts/patches/sql/pre-db-import/*.sql`** — data fixes the new `ac-db-import` needs before it can run, applied only by `upgrade-azerothcore.sh` (`apply_pre_db_import_sql LABEL MYSQL_CMD…`), in file-name order, through `mysql -N -B` on stdin. `rehearse` applies them to `acup-rehearsal-db` right after the drill restore and before the candidate db-import (failure = `[FAIL]`, log `rehearsal-<ts>/pre-db-import.log`, db-import not run). `cutover`'s boot step applies them to `ac-database` (running since the stop step) after `BOOT_STARTED` and before `compose up`, then records `PRE_DB_IMPORT_APPLIED=1` (flushed; shown by `status`); a failure goes through `stop_realm_and_die` (stack not started; fix and resume, or roll back — the DBs are restored). Guard design: plain SQL cannot fail conditionally, so each file carries exactly one `-- guard: <SELECT returning a count>` line (all files are checked for it before the first runs); the shell runs it after its file and requires exactly `0` — a mysql error, a failing guard query or any other count fails closed. Files must be idempotent: a resumed boot step re-applies them, also after db-import ran. The boot step runs `docker exec ac-database` right away, without waiting for the database to be healthy, so a `cutover --state DIR` resume right after a host reboot must first wait until `ac-database` reports healthy (else the SQL fails against a database still starting). Their sha256s feed `SQL_PATCHES_SHA256` in the build fingerprint, so editing one invalidates the stage and its rehearsal ("re-run stage") and a resumed cutover refuses it. `0001-mod-ip-fixed-gameobject-guids.sql` (the 2026-10-27 rehearsal's `ERROR 1062 Duplicate entry '5714442' for key 'gameobject.PRIMARY'`): the old mod-individual-progression (`636ba4c6`) inserted six gameobjects by AUTO_INCREMENT (`aq_gate_quest.sql`, `naxx40_gameobjects.sql`) that got guids 5714438–5714443 here; core update `2026_08_08_09.sql` hard-codes 5714442–5714445, and DBUpdater applies core updates (sorted by file name) before the module files, whose new revision (`4933d455`) re-inserts those spawns at fixed guids. The file moves each row to the new module's guid (650111–650113, 361001–361003; 193166 only on map 0 — its map-571 row is core) with `UPDATE … WHERE guid <> target AND NOT EXISTS (SELECT 1 FROM (SELECT … LIMIT 1) AS t)`; its guard counts the six spawns still at guid ≥ 5714438. On the next upstream bump, check new core updates' hard-coded guids against this server's AUTO_INCREMENT rows the same way. The installer never needs it (a fresh world has no old rows).

**Upgrades go only through `scripts/upgrade-azerothcore.sh`** (`preflight | stage | rehearse | cutover | rollback | finalize | status`; `--dry-run` prints every mutating command). `preflight --previous-repo-rev REV` (REV = the revision of this repo whose tooling the live stack was installed with) is read-only go/no-go; `stage` builds a staging checkout, candidate images (`acore/ac-wotlk-*:upgrade-<sha12>`) and client data while the live stack keeps running; `rehearse` boots the candidate against a restored backup on an isolated network (`acup-*` objects only); `cutover [--pin AC_K=V]…` is the only disruptive step (cold `preupgrade` backup, switch, boot, verify); `rollback` returns to the exact pre-cutover state (code, images, configs, DB via `restore-azerothcore.sh`, whose revision guard passes because the revisions match again); `finalize` deletes the rollback artifacts (image and git tags, client-data copies, the staging checkout recorded in the cutover state — `preupgrade`/`prerollback` archives stay until deleted by hand). Work root `$UPGRADE_ROOT` (default `~/azerothcore-upgrade`). `cutover`/`rollback` are live lifecycle operations: run them only on explicit user request (see the safety rules). `redeploy-azerothcore.sh` is **not** an upgrade tool.

**Upgrade safety invariants (keep them when touching `upgrade-azerothcore.sh`).**
- *One run at a time:* every state-changing subcommand takes `flock -n` on `$UPGRADE_ROOT/.lock`. Repository-spec loops read `upstream_repo_specs` on fd 3 so a command inside cannot swallow the list.
- *Provenance:* `stage` records its build inputs (four `*_REV`, `CLIENT_DATA_VERSION`, versions-file, patch-set and pre-db-import-SQL-set sha256) and `BUILD_FINGERPRINT` in `staging/stage-<sha12>.env`; `rehearse` and a fresh `cutover` refuse a stage built from other pins or patches ("re-run stage"). `rehearse` writes all four `CANDIDATE_ID_*`, the fingerprint and its sorted `--pin` set to `result.env`; the cutover's rehearsal gate requires all of them to equal the stage and the cutover's `--pin` set. The cutover records `STAGING_SRC`, `BUILD_FINGERPRINT`, `ADMIN_PRESENT` (image `azerothcore-admin:local` and `$ADMIN_STACK_DIR/docker-compose.yml` both present; when false every admin step is skipped, and a stray running `azerothcore-admin` container is stopped and left stopped, with a log line at the stop and admin steps) at start.
- *Client-data rollback copy:* `stage` copies the live volume into `acup-client-data-rollback-<ver>` and only a finished copy carries `.acup-complete` (entry count + regular-file byte total of the source, marker excluded); `stage` refuses while `current` is a cutover without `CUTOVER_OK`/`ROLLED_BACK` or with an unfinished rollback (the live volume may be partial). It re-copies only a volume that is not a complete copy by itself (missing, wrong data-version, no marker, marker BYTES not all digits (an older script's rounded total, e.g. `3.23188e+09`), tree ≠ marker); a complete copy that differs from the live volume is never overwritten: stage dies and the operator inspects and removes it by hand. The cutover verifies the copy read-only (exists, marker, data-version = `CLIENT_DATA_LIVE`, totals = marker = live volume) before `confirm UPGRADE` and again right before `CLIENT_DATA_SWITCH_STARTED` (on a resumed switch only against the marker), always probing with the live client-data image; `rollback` checks it against the marker before stopping anything and, after copying it back, requires the live volume to hold `CLIENT_DATA_LIVE` with exactly the marker's totals (else it dies; safe to re-run).
- *Started markers* (`SWITCH_CODE_STARTED`, `CLIENT_DATA_SWITCH_STARTED`, `IMAGES_SWITCH_STARTED`, `BOOT_STARTED`, `ADMIN_STEP_STARTED`) are written and `sync`ed immediately before a step's first mutation; `STEP_<name>` after it. Rollback decides from them what to undo (any code switch, image switch or boot ⇒ the databases are restored).
- *Stop step:* requires `ac-worldserver` `Status=exited`, `ExitCode=0`, `OOMKilled=false` (else its last saveall may be incomplete) before the cold backup, then records `STOPPED_AT`. `rehearse` checks the candidate's exit code likewise: after its `docker stop -t $STOP_TIMEOUT`, a non-zero `acup-rehearsal-world` exit code fails the rehearsal.
- *Resume guards* (`cutover --state DIR`): refuse a rolled-back cutover, a rollback in progress (`ROLLBACK_STARTED` without `ROLLED_BACK`), changed pins/candidate tag/`BUILD_FINGERPRINT`, different `--pin` values (recorded ones are replayed), candidate images changed since start, the 02:30–03:45 UTC window, and — between the stop step and `BOOT_STARTED` — any `ac-worldserver`/`ac-authserver`/`ac-db-import` that is up or has `StartedAt` after `STOPPED_AT` (a reboot ran the half-switched stack: roll back). A resume re-stops an admin app a reboot started, until `ADMIN_STEP_STARTED`. `UPGRADE_NOW_UTC_MIN` is a test-only clock seam.
- *Counts:* verification compares the cold backup's account and character counts with the upgraded boot's, each separately: a decrease (or an unreadable count) stops the realm; an increase prints `WARNING: <accounts|characters> B -> A (+N) since the cold backup …`, records `COUNTS_WARNING` in `state.env` (shown by `status`, repeated at the end) and continues — a player or the bot pool may create one during boot, so check before opening the realm.
- *Never half-up:* from the boot step to the end of verification an `ERR` trap (with `set -E`) routes any failure, including a count query or step marker, through `stop_realm_and_die`, which re-checks the containers and prints `STILL RUNNING: <name>` instead of "Server is stopped" when a stop did not take.
- *Rollback:* refuses local files that collide with the `OLD_REV_*` trees before stopping; after `snapshot_state` it saves (`patches-rollback/`) and discards tracked edits in the core and the modules, then re-applies `patches-live/<label>.diff` only when `git apply --reverse --check` says it is not applied. After go-live (`BOOT_STARTED`) it first takes a cold `backup.sh --label prerollback` and copies that archive + sha256 and the current `override.yml`, `admin.yml`, `configs/`, `env/dist/etc` into `cutover-<ts>/pre-rollback/` (once: `PRE_ROLLBACK_BACKUP=1`); if that backup fails it refuses with the realm stopped and nothing overwritten, unless `--no-safety-backup`. The DB restore runs `restore-azerothcore.sh --keep-archive-realmlist` (no fresh-realmlist read/rewrite, so a re-run after the DROP works). Once code, configs, client data, images, DBs, the stack and the admin are back it records `ROLLBACK_RESTORED=1`; from then a re-run only waits for `World Initialized` and runs the previous verifier, a verifier failure is an open item (not an unfinished rollback), and `rollback --accept-verify-failure` records `ROLLED_BACK` on the operator's judgment.
- *`--previous-repo-rev`:* preflight FAILs when that commit's `scripts/upstream-versions.env` pins other revisions than the live checkouts' HEADs (its verifier judges the rollback). The plan's REV is `ec93de3` (pre-pinning, no Check 15 checksum compare). A REV whose verifier compares `backup.sh` (Check 15, PR 1 onward) FAILs that check after a rollback, because the deployed `backup.sh` is this branch's (it knows `prerollback`): read `rollback-verify.log`, then `--accept-verify-failure` if that is the only failure.

**`scripts/migrate-ac-env.sh` carries the overlays across mod-playerbots #2854** (spec U-1): every config key `AiPlayerbot.X` became `Playerbots.X` (suffix unchanged, **no fallback**), so old keys and every `AC_AI_PLAYERBOT_X` env var are silently ignored and bots run on defaults (500 bots, `BotActiveAlone=10`, `TravelFlight=15`, …). All 23 distinct `AC_AI_PLAYERBOT_*` names in this server's live overlays (`override.yml` 9, `admin.yml` 20) map 1:1 to `AC_PLAYERBOTS_*` (prefix swap); the installer ships 9 of them. The script copies both overlays to `--backup-dir` (mode 700), swaps the prefix, refuses if both names of a pair are set, rewrites **in place** (open+truncate — `admin.yml` is a bind-mount source), and with `--validate-against FILE.conf.dist` (repeatable) checks every migrated/pinned name against `config_key_to_ac_env_var` over the new dists (`AC_PLAYERBOTS_DATABASE_INFO` exempt). `--pin AC_K=V` appends pins to the `ac-worldserver` environment block of `admin.yml` so an upstream default change cannot silently alter this server; it refuses to change an existing different value or to guess an unexpected layout. `--dry-run` prints a diff. A fresh install needs no migration: the installer heredoc, grep arrays and `managed_vars` already use the new names.

**Verifier checks for this** (`verify-azerothcore.sh`): **Check 11's tail (informally 11b)** FAILs when `playerbots.conf` still has `AiPlayerbot.*` lines (the old prefix is assembled at runtime so `test_no_pre_rename_playerbots_names_remain` can forbid the literal in the file). **Check 23**: every `AC_*` in `docker-compose.admin.yml` reverse-maps to a loaded key (Check 12's `env_to_key`) *and* is in the worldserver container env; INFO-skipped when Check 12 could not read the loaded config. **Check 24**: each checkout's `HEAD` equals its pin (via `upstream_repo_specs`) and `apply-local-patches.sh --check` passes; skipped when `upstream-versions.env`/`lib/` do not sit next to the verifier. **Check 25** (current boot only, `docker logs --since StartedAt` streamed once through `grep -a`, never captured whole — the json-file log is unbounded): FAILs on any `Missing property` (stale `.conf` or unmapped key) and on `built with generator` (stale mmaps; the error is `LOG_ERROR("maps")` → root logger → console + `Server.log`, **not** `Errors.log`, so pathfinding can be broken with an empty `Errors.log`). **Check 26**: `INSTALLED_VERSION` in `/azerothcore/env/dist/data/data-version` equals `CLIENT_DATA_VERSION` (needs Check 24's load). **During an upgrade, a live stack not yet cut over to new pins FAILs Check 24 and Check 26 by design** (for the 2026-10 upgrade also Check 8, Check 11's tail and Check 12, which expected the `AC_PLAYERBOTS_*` names), and Check 15 until the new `backup.sh` is deployed (preflight requires that anyway); Check 25 inspects only the current boot and passes on a self-consistent old boot. `verify-azerothcore-admin.sh` step 9 delegates to the AC verifier, and `redeploy-azerothcore-admin.sh` (`:207`) runs that admin verifier on its candidate and rolls back on failure, so **admin redeploy is blocked between merging new pins and the cutover**. The admin *installer* is not gated: it only prints a "Verify with: …" hint (`install-azerothcore-admin.sh:264`).

**`env/dist/etc/*.conf` and module `.conf` files are never refreshed** (spec U-7): module confs are seeded only when missing by Phase 3.1's `if [ ! -f "$conf" ]; then cp "$dist" "$conf"` loop (`install-azerothcore.sh:3366-3375`), and `env/dist/etc/*.conf` by upstream's container entrypoint, which likewise copies only missing files. After an upstream bump a stale file logs `Missing property` for every new key (Check 25) and one with removed/renamed keys silently runs defaults; an upgrade has to replace them explicitly.

**Admin key index (Settings) is built from the AC source tree.** `stage_conf_dists` (in both `install-azerothcore-admin.sh` and `redeploy-azerothcore-admin.sh`) copies `src/server/apps/worldserver/worldserver.conf.dist` and `modules/{mod-playerbots/conf/playerbots,mod-ah-bot-plus/conf/mod_ahbot,mod-individual-progression/conf/individualProgression}.conf.dist` from `$AC_STACK_DIR` (default `/opt/stacks/azerothcore`) into the build context's `dist/`, so the index always matches the deployed version. If any of the four is missing it warns and falls back to the gitignored `docs/configs/*.conf.dist` — refresh those after an upgrade. `tests/data/env_var_golden.txt` is generated from the pinned dists (1996 keys).

## Non-obvious internal conventions

**Upstream fork.** Phase 1 clones `mod-playerbots/azerothcore-wotlk` on branch `Playerbot` (not canonical `azerothcore/azerothcore-wotlk`); the three modules are cloned as subdirs of its `modules/`. Every checkout is then pinned to `scripts/upstream-versions.env` and locally patched — see *Pinned upstream + upgrades*.

**`AC_*` env var derivation.** AzerothCore derives env-var names from config keys: prefix `AC_`, replace dots/spaces/hyphens with `_`, insert `_` at lowercase→uppercase and letter→number boundaries, uppercase. E.g. `Playerbots.Enabled`→`AC_PLAYERBOTS_ENABLED`, `Respawn.DynamicRateGameObject`→`AC_RESPAWN_DYNAMIC_RATE_GAME_OBJECT`, `SkillGain.Crafting`→`AC_SKILL_GAIN_CRAFTING`. **Unknown env vars are silently ignored** — when adding an `AC_*` line, verify the target key exists in the relevant `.conf.dist` (the pinned checkout's, e.g. `modules/mod-playerbots/conf/playerbots.conf.dist`; `docs/configs/` copies can be stale) or it's dead weight. This is not hypothetical: mod-playerbots #2854 renamed every `AiPlayerbot.*` key and orphaned every `AC_AI_PLAYERBOT_*` var at once (see `migrate-ac-env.sh` below).

**`docker-compose.override.yml` is the single source of truth for AC tuning.** Every static `AC_*` in Phase 2.5's heredoc is mirrored by a verification grep array right below it and listed in the Phase 2.6 `for var in …` effective-compose check. Prompt-substituted values (`PLAYERBOT_COUNT`, `MAP_UPDATE_THREADS`, `SERVER_PVP`) and XP-rate values have dedicated checks. When adding/removing an `AC_*`, update the heredoc, the Phase 2.5 grep array, and the Phase 2.6 list — skipping any lets a missing/corrupted override pass install silently.

**Rename-detection / silent-drop check.** Phase 4 (`verify_managed_env_vars_bound_in_worldserver`) and `verify-azerothcore.sh` (Check 12) confirm every managed `AC_*` is present in the running `ac-worldserver` env and reverse-maps (via AC's real Config.cpp rule) to a key in the loaded `worldserver.conf`/module `.conf` files. This catches an upstream rename or typo that invalidates an `AC_*`; Check 23 applies the same reverse-map to every `AC_*` in `docker-compose.admin.yml`. Keep in sync when adding/removing an `AC_*`: the Phase 2.5 grep array, the Phase 2.6 list, the install helper's `managed_vars`, Check 12's `managed_vars`, and `OVERRIDE_EXPECTED` in `verify-azerothcore.sh`. `AC_PLAYERBOTS_DATABASE_INFO` is excluded (a connection string, verified indirectly by `acore_playerbots` access); XP-rate vars are included only when `SERVER_XP_RATE != "x1"`. (`Server.log` binding lines are evidence but not authoritative — AC logs a binding only when the env value differs from the loaded `.conf` value.)

**`AuctionHouseBot.GUIDs` is the one `.conf`-side write.** Written to `configs/modules/mod_ahbot.conf` in Phase 6.1.4 because the comma-separated AH bot GUIDs are runtime-discovered after pause-3 and don't fit one env var. `EnableSeller`/`Buyer.Enabled` use env vars (`AC_AUCTION_HOUSE_BOT_ENABLE_SELLER`/`AC_AUCTION_HOUSE_BOT_BUYER_ENABLED`). Don't add other `.conf`-side writes — add an `AC_*` to the Phase 2.5 heredoc instead.

**`set_conf_key` vs `require_conf_key_once`.** `set_conf_key` removes _all_ existing occurrences of a key and appends one canonical line (avoids AC's duplicate-key warning); `require_conf_key_once` only validates exactly one occurrence exists, never modifies. Their only remaining callers are the `AuctionHouseBot.GUIDs` write/assert pair in Phase 6.1.4 (`install-azerothcore.sh:3902`/`:3904`). They (plus `escape_regex_metachars`) survive solely because GUIDs are runtime-discovered after pause-3.

**`PLAYERBOT_COUNT` non-interactive seed.** In non-interactive mode the bot-count default reads from `$AC_PLAYERBOTS_MIN_RANDOM_BOTS` (AC's real env-var name, reused so AC docker docs carry over). Don't rename it to a script-local `PLAYERBOT_*` var.

**`--adopt` mode** verifies existing stack state before marking phases complete and aborts if verification fails (desired). Don't add a `--force-adopt` bypass without explicit request.

**`xp_rate_values` field order** is always `quest kill explore money reputation skill_discovery item_normal item_uncommon skill_crafting skill_gathering skill_weapon skill_defense`. The `read -r` destructuring in `insert_xp_rate_overrides_into_compose` and both verify helpers depends on it.

**`save_config` GUID preservation.** It rewrites `~/.azerothcore-install-config` from scratch but appends `AHBOT_GUIDS` if non-empty, preserving GUIDs across config rewrites after Pause 3 (e.g. retrying an earlier phase).

**`compose_scale_args` empty-array guard.** Returns no output (not even a newline) when nothing needs scaling down. Callers `mapfile -t` the args; a blank line would yield a one-element empty array that breaks `docker compose`.

**`INNODB_BUFFER_POOL_INSTANCES` is derived, never persisted.** Computed as `${INNODB_BUFFER_POOL_SIZE%G}` after both prompt branches converge (right after the `SERVER_XP_RATE` backfill). Deliberately not in `save_config`/`load_config` — recomputation is canonical so a stale config can't desync it. 1 GB per instance keeps each above MySQL's honoring threshold.

**Optional direct-LAN play (`LAN_IP` prompt, AC side).** Phase 2.5's heredoc ships a second `ports:` line for `ac-worldserver` (`"127.0.0.1:8085:8085"`) and `ac-authserver` (`"127.0.0.1:3724:3724"`); anchored sed replaces `127.0.0.1` with `LAN_IP` when set (127.0.0.1 = "off"; never an empty host IP → `0.0.0.0`). They live in `override.yml`, not `.env`, because the upstream compose has one `${DOCKER_*_EXTERNAL_PORT}` entry per service and Compose appends override ports by host IP. Phase 5 sets `realmlist.localAddress`/`localSubnetMask` from the LAN IP's interface prefix (or restores `127.0.0.1`/`255.255.255.0`): AC's `Realm::GetAddressForClient` (`Realm.cpp`) returns `localAddress` only to clients inside that subnet, so Tailscale (100.x) clients keep `address`. `verify-azerothcore.sh` reads the LAN IP back from the override's auth line: Check 6b compares `localAddress` (FAIL) and reports assignment/sysctl (INFO); Check 21 allows the LAN/loopback listener on 3724/8085. `LAN_IP` is persisted in `save_config` and backfilled blank for older configs. `--adopt` never prompts for it — adopt skips Phase 2.5, so it reads the existing override's LAN line (`existing_override_lan_ip`) instead; a prompted IP would reach the realmlist with no listener. The AC systemd unit has a second, non-fatal 30 s `ExecStartPre` LAN-IP wait (reads the IP from the override).

**`playerbots.conf` is seeded but never edited by the installer.** Phase 3.1 copies any `*.conf.dist`→`.conf` if missing (`install-azerothcore.sh:3366`), then never touches it. Env vars in `override.yml` win at config-read time, so its content is **not** the source of truth — stale `set_conf_key` values in a long-running install's `playerbots.conf` are cosmetic. Verify Check 11 asserts the file exists and, beyond that, only that no pre-rename `AiPlayerbot.*` key remains (mod-playerbots reads `Playerbots.*` since #2854; a leftover old-style file is a stale template, not an override).

## Known-benign log noise

These appear in a healthy install — don't chase them as bugs. The canonical "is anything broken?" signal is `Errors.log`: 0 bytes, or only the known-harmless lines below (dashboard banner neutral, not red; Check 16 INFO, not FAIL) = no real runtime errors.

**Install log, Phase 3 build only:** hundreds of clang `-Wsign-compare`, `-Wdeprecated-copy-with-user-provided-copy`, `-Wimplicit-const-int-float-conversion`, and `"N warnings generated"` lines from `modules/mod-playerbots` and core sources (upstream code built with `-DWITH_WARNINGS=ON`). Build still succeeds; don't "fix" them here.

**Install log, Phase 4:** the `ac-client-data-init` download is ~1.2 GB for client data `v20.0` (the installer's own progress text still says ~600 MB — stale). The wait loop gives the init container 30 min.

**`Server.log`:**
- `mysql: [Warning] Using a password on the command line interface can be insecure.` — every time a script shells out to `mysql -p`; deliberate for non-interactive use.
- `Can't set process priority class, error: Permission denied` — worldserver can't raise priority without `CAP_SYS_NICE`. Cosmetic; don't add the cap.
- `MoveSplineInitArgs::Validate: expression 'velocity > 0.01f' failed for GUID …` — upstream world-DB quirk (zero-velocity spline data). Cosmetic.
- `>> The file 'YYYY_MM_DD_NN.sql' was applied … but is missing in your update directory now!` — high-volume (~2500+/boot) DBUpdater message for every applied SQL file absent from `data/sql/archive/db_<name>/`. Each DB still ends `>> <Name> database is up-to-date!` — informational. (Upstream fix is shipping populated `archive/db_*` dirs; this build doesn't.)
- **Not benign, despite landing only in `Server.log`:** `Missing property …` (stale `.conf` or unmapped key) and `… built with generator …` (mmaps built by a different generator version than the core expects — no pathfinding; `Errors.log` stays empty). Verifier Check 25 catches both for the current boot.
- A frozen `Server.log` mtime after `WORLD: World Initialized` is normal — the Server appender goes quiet; runtime traffic routes elsewhere. Check `Errors.log` size and `docker logs --tail 20 ac-worldserver` before suspecting a stall.

**`Playerbots.log` / `docker logs ac-worldserver`:**
- `<Bot> A:<action> - FAILED` (e.g. `A:follow`, `A:add gathering loot`, `A:reset botAI`) and `Can cast spell failed. No spellid. - spellid: 0, bot name: <Bot>` — the module logs every inapplicable action-tick (retry/inapplicability traces). High volume is normal; not errors.
- `Random teleporting bot <Name> (level N) to Map: … (i/k locations)` — normal `RandomBot` periodic re-distribution.
- `Random Bots Stats: 0 online` (Active/Moving/In flight/In combat all 0) is the **expected steady state with no real player logged in.** `AC_PLAYERBOTS_DISABLED_WITHOUT_REAL_PLAYER=1` (in `override.yml`) gates the random-bot login engine on real-player presence — characters aren't deleted, just kept `online=0`. The pool (250 `RNDBOT*` accounts × 10 chars ≈ 2500 characters, split 200 RNDbot / 50 AddClass per `acore_playerbots.playerbots_account_type`) persists across restarts; graceful shutdown sets all `online=0`. A real player ramps active bots toward `AC_PLAYERBOTS_MIN_RANDOM_BOTS`. Verify pool integrity: `docker exec -i ac-database mysql -uroot -p"$DOCKER_DB_ROOT_PASSWORD" -e "SELECT COUNT(*) FROM acore_characters.characters c JOIN acore_auth.account a ON a.id=c.account WHERE a.username LIKE 'RNDBOT%'"` ≈ 2500.

**`Errors.log` — `Table `graveyard_zone` incomplete: Zone <id> Team <0|1> does not have a linked graveyard`** (`sql.sql` channel): an upstream **data gap**, not corruption. AC ships no `graveyard_zone` link for a few zones a real player never dies in — notably **2037 Quel'thalas** (map 0) and **3455 The North Sea** (map 530). Playerbots roam/teleport/drown there, so it surfaces only after hours of uptime (one line per death). Benign — `GetClosestGraveyard` (`GameGraveyard.cpp:168`) falls back to the default GY (Westfall/Crossroads) — but it breaks the "0 bytes = clean" invariant. Fix = add a neutral (`Faction=0`) `graveyard_zone` row per zone pointing at the nearest existing graveyard, then `reload graveyard_zone` in the console (no restart). This server applied it live (1448→2037, 922→3455); it is **not** baked into the installer, so a fresh world import reintroduces the noise. Exact SQL + revert: gamemaster `ref-troubleshooting.md`.

**`Errors.log` — `Pool Id <id> is empty (has no creatures, no gameobjects, no quests and no valid child pools). The pool will not be spawned.`**: a **mod-individual-progression orphan**, benign (issue #47) — not an upstream AC data gap. Currently exactly one line, pool 1072 ("Mirelow" 14424, a rare spawn): AC ships it with 22 spawn points, and the module's `data/sql/world/base/zone_wetlands.sql` (`-- missing patrols`) deletes all its `pool_creature` rows and spawns one waypoint-patrolling Mirelow instead (guid 91113, path 911130), but keeps the `pool_template` row — every other pool the module empties it also deletes or refills. The world DB has carried it since the module first applied; cores since azerothcore-wotlk #27026 (2026-08-08: deleted AC's own 74 memberless pools and raised this message to error level, as TrinityCore asserts on it) log it once at startup. No gameplay effect: Mirelow spawns and patrols as a plain creature; only the unused pool never spawns. Check 16 allow-lists it (`empty-pool-1072`: anchored pattern, pool 1072 only): a file holding only known-benign lines gives an INFO naming them, mixed content or a near-miss line still FAILs. Deliberately not fixed locally: the fix is one line in the module (`DELETE FROM pool_template WHERE entry = 1072;`); a live one-row delete would survive module re-applies (the file never re-inserts the template), but a fresh world import brings it back. Any *other* pool id stays actionable (red on the dashboard, FAIL in Check 16) — check it after an upgrade.

**`Errors.log` — `SmartScript::ProcessAction: SMART_ACTION_TALK: EntryOrGuid 16878 SourceType 0 EventType 61 TargetType 7 using non-existent Text id 0 for talker <n>, ignored.`**: an upstream SmartAI quirk, benign. Shattered Hand Berserker's (16878) enrage emote row (`smart_scripts` id 4, `target_type=7` ACTION_INVOKER) makes the *invoker* the talker; when that is a bot's guardian summon (Spirit Wolf 29264, …) it has no `creature_text`, so only the emote is skipped (no `TEXT_OVER` chain depends on it). Allow-listed for this exact row only, any talker id; every other `SMART_ACTION_TALK` line stays actionable — a skipped line can stall a scripted event, so fix those per row (gamemaster `ref-troubleshooting.md`).

**Known-harmless `Errors.log` lines are one shared list.** `KNOWN_ERRORS` in `wow-server-sp-admin/app/services/known_errors.py` (key, pattern, title, reason) and `KNOWN_ERRORS_LOG_PATTERNS` in `verify-azerothcore.sh` Check 16 (`'key|ERE'`) must stay identical: `scripts/tests/test_known_errors_parity.py` compares them and runs every pattern through both `grep -E` and Python `re` on sample lines, so patterns stay in the common subset (literals, `[...]`, `+`/`*`, escaped `\.`/`\(`/`\)`, `^`/`$`). Current keys: `graveyard-zone`, `empty-pool-1072`, `smart-talk-16878`. Add an entry only for a verified line, with exact wording and numeric ids (a near-miss must stay actionable), in both places plus a reason a player-admin can read. The dashboard classifies the **whole** file (`summarize_errors_log`, ≤ 1 MiB, larger = red unread; blank lines ignored): empty → green; only known lines → neutral "Only known harmless warnings (N)", Errors.log tab not dirty, a "Summary: known harmless warnings" section (title, reason, count) above a "Raw log: last 40 lines" section, and each known line dimmed with a KNOWN tag; any unknown line → red "N runtime errors detected (+K known harmless)". Check 16 prints INFO naming the keys present. Known lines are marked, never hidden.

## Non-obvious admin app conventions

Invariants of `wow-server-sp-admin/` to know before touching admin code — or before changing anything in `install-azerothcore.sh` the admin reads (env-var derivation, mounts, config paths). Internal details (snapshots, runner, SSE) live in the design spec.

**Admin's only writes inside `/opt/stacks/azerothcore/` are `docker-compose.admin.yml` and `backups/`.** The whole `/ac/` mount is ro except those two rw sub-mounts. The admin never edits `override.yml`, AC's `.env` (the installer does, once), any `.conf`, MySQL `custom.cnf`, or `data/`. In-app Restore writes DBs via `docker exec ac-database` and restores `docker-compose.admin.yml` only; host-side configs are restored by `scripts/restore-azerothcore.sh` (fresh-machine recovery). Installer-shipped defaults remain owned by the Phase 2.5 heredoc.

**One installer-time touch outside the admin stack dir:** `install-azerothcore-admin.sh` appends `docker-compose.admin.yml` to AC's `.env` `COMPOSE_FILE=` line (idempotent). Regenerating AC's `.env` via the AC installer loses it — re-run the admin installer to restore.

**`docker-compose.admin.yml` is the LAST-precedence Compose layer** (merges last in `COMPOSE_FILE` order, overriding the same key in `override.yml`). Same silent-drop trap applies. The Apply flow runs the same two-part check as `install-azerothcore.sh:verify_managed_env_vars_bound_in_worldserver` (presence in `docker exec ac-worldserver env` + reverse-map to a loaded `.conf` key). `config_key_to_ac_env_var` in `wow-server-sp-admin/app/services/env_var.py` is golden-file-tested against the bash helper over all ~1996 keys in the four pinned `.conf.dist` files — both must agree exactly or the check yields false negatives.

**`AuctionHouseBot.GUIDs` is in admin's `BLOCKED_KEYS`** — installer-managed and runtime-discovered, so the admin refuses to write it server-side regardless of the client. Don't make it admin-editable.

**Progression page: internal key `"vanilla"` displays as `"Classic"`.** `EXPANSION_LABELS`/`EXPANSION_ICONS`/`TARGET_STATES` and all JS in `partials/progression_page.html` use `"vanilla"`; icon file is `classic.png`; UI label is `"Classic"`. Don't rename the internal key — it flows through DB queries, the service, and template JS.

**Progression data is embedded once, not fetched separately.** `api_progression_characters` serialises all character rows to `rows_json` injected into a `<script type="application/json" id="progression-char-data">` tag; client JS builds the dropdown and list from that blob. No second API call, no Refresh button by design; `hx-trigger="load"` fires once.

**Players page + dashboard "Online" card: "online" = PresenceTracker human, `latency > 0` fallback (issue #32).** One pure rule, `players.online_humans(rows, presence)`, is shared by `collect_players()` (Online now card, headline count, All characters "online" label via `CharRow.online_now`) and `db_stats.count_online()` (dashboard card) so they always agree. **Admin publishes on Tailscale + an optional LAN bind.** `docker-compose.yml` has two `ports:` entries: `${TAILSCALE_IP}` (always) and `${LAN_IP:-127.0.0.1}` — the loopback fallback is deliberate, because an empty host IP would make Docker publish on `0.0.0.0`. The installer takes `LAN_IP` from the environment (`LAN_IP=` disables it) or keeps it from the existing `.env`, and rejects an IP that is unassigned or equal to the Tailscale IP. AC's authserver/worldserver have their own, separate LAN bind (see *Optional direct-LAN play*). `ExecStartPre` snippets must avoid `${…}` (systemd substitutes it inside words).

**LAN binds (admin and AC) are best-effort and depend on a host setting outside the repo: `net.ipv4.ip_nonlocal_bind=1`.** Docker refuses to publish on an IP the host doesn't currently have (`cannot assign requested address`), and that failure takes down the *whole* container — Tailscale bind included, i.e. `ac-authserver`/`ac-worldserver` for every player — e.g. after a DHCP lease change, a moved cable, or a migration to a machine with a different LAN IP. `/etc/sysctl.d/99-nonlocal-bind.conf` containing `net.ipv4.ip_nonlocal_bind=1` lets the bind succeed anyway, so Tailscale keeps working and the LAN bind comes alive once the IP returns. The repo only *detects* it (installer WARNING, verifier `[INFO]`); it never sets it. The systemd unit's LAN-IP wait is 30 s and non-fatal (warns, then starts). **On any host change** (new machine, new router, new subnet): set the sysctl; update/clear `LAN_IP` in `azerothcore-admin/.env` and redeploy the admin; update the two AC LAN port lines in `docker-compose.override.yml` (recreate `ac-authserver`/`ac-worldserver`) and `realmlist.localAddress`/`localSubnetMask`; give the server a DHCP reservation on the router — clients' `realmlist.wtf`/hosts-file entries point at that IP too. A new machine also needs its own `TPM_DEVICE`/`TSS_GID` in the admin `.env` (see *Cloud backup*): a stale `TPM_DEVICE=/dev/tpmrm0` on a host without that device makes Docker refuse to start the admin container (the device mapping fails) — set `TPM_DEVICE=/dev/null` (or delete the line and redeploy; the backfill re-resolves it); a `data/cloud/` copied to another machine cannot unseal there (the panel says "Can't unlock the stored session"), so press Reconnect.

**Admin container needs `group_add: ["${DOCKER_GID}"]`.** It runs as non-root (`HOST_UID:HOST_GID`) so its writes own correctly, but that user can't reach `/var/run/docker.sock` by default — every Docker SDK call would `PermissionError(13)`. The installer resolves the host docker-group GID (`getent group docker`) into `.env`; `docker-compose.yml` mounts it via `group_add`. Don't remove it.

**`admin.yml` writes are in-place (open+truncate), not tmp+rename** — it's a bind-mount source inode, so `rename(2)` over it fails with EBUSY. Crash safety = snapshot-before-write (snapshots in `/admin-snapshots/`, 7-day GC on boot); both snapshot and write run under the action runner's single-flight lock (`pre` hook). By contrast `maintenance.json` is a regular file in `ADMIN_DATA_DIR`, not a bind-mount source, so it uses atomic tmp+rename (`os.replace`).

**`Server.log` wait is truncate-aware.** AC's `Appender.Server=…,Server.log,w` opens fresh each boot, truncating the file. `_wait_for_world_init` baselines `last_size` at entry and resets to `0` on a size drop — else a stale prior-boot "World Initialized" line trips a false positive on Restart. Revisit if you change the Server.log appender mode.

**Admin's Stop does NOT use `server shutdown N`.** AC's SIGTERM handler (`World::StopNow`) instantly collapses any in-progress countdown, and `docker stop` sends SIGTERM first. So the admin holds the grace window itself (`time.sleep`), sends `announce`/`notify`/`saveall` over `docker attach` stdin (detach bytes `\x10\x11`), then `docker stop --time 60 ac-worldserver` (60 s because clean saveall can take 30–45 s under bot load; avoids Docker SIGKILL mid-save), then polls for `Status=exited` on its own 120 s budget.

**Admin console attach must use a raw PTY, not `subprocess.PIPE`.** The worldserver container has `Tty=true`/`OpenStdin=true`; from the non-interactive admin container, `docker attach` with a pipe dies (`cannot attach stdin to a TTY-enabled container …`), breaking Restart and Apply. `wow-server-sp-admin/app/services/console.py` opens a PTY, sets the slave raw, passes the slave FD as Docker's stdin, writes commands + `\x10\x11` via the master, waits for Docker to consume the detach, then closes. On clean raw-mode detach Docker may exit 1 with stderr `read escape sequence` — that's the detach ack, not a failure.

**Backup architecture is one shared script.** `scripts/backup.sh` is canonical. Phase 7 deploys it to `/opt/stacks/azerothcore/backup.sh` for host cron with `install -m 0755` (it unlinks the destination first, so it also replaces a root-owned copy left by a manual `sudo cp`); `verify-azerothcore.sh` Check 15 `cmp`s the deployed copy against `scripts/backup.sh` and FAILs on drift (INFO "cannot compare" when no `backup.sh` sits next to the verifier). Admin install/redeploy bundle the same file as `/app/scripts/backup.sh` with `STACK_DIR=/ac`. It produces one consolidated `azerothcore-backup-<label>-<stamp>.tar.gz`: `manifest.json` + `sql/azerothcore.sql` (one `mysqldump` transaction spanning all four DBs) + staged `config/` (`.env`, both compose overlays, `configs/`, the generated `etc/*.conf` from `env/dist/etc/`, and `admin-data/{maintenance,presence}.json`). The v2 manifest records `git_revisions` (core + 3 modules), `ac_image`, `images` (worldserver/authserver/db-import/client-data image IDs), `client_data_version` (first line, `A-Za-z0-9._-` only, since it is interpolated into the JSON) and `backup_script_sha256` (`unknown` if hashing fails — never fatal). `ADMIN_DATA_DIR` defaults to `$(dirname "$STACK_DIR")/azerothcore-admin/data` in both `backup.sh` and `restore-azerothcore.sh` (the admin container sets `/admin-data` explicitly), so a sandboxed stack dir never reaches live admin data; both scripts log what they captured/skipped when a dir is absent. No `backup_runner.py`, no per-DB/config-tarball multi-file format.

**`${STACK_DIR}/backups/.backup.lock` is one shared cross-process lock**, non-blocking `flock`. Three call sites hold it: `backup.sh` itself, host `restore-azerothcore.sh`, and the admin's in-app restore (`actions.py`'s `_backup_mutation_lock`). The admin acquires it only *after* its own pre-restore safety backup completes — that safety backup shells out to `backup.sh`, which takes/releases the same lock itself, so acquiring earlier would self-deadlock. Contention → busy failure, no mutation, not a wait.

**Admin redeploy uses its own `${STACK_DIR}/.redeploy.lock`** (non-blocking `flock`, disjoint from `.backup.lock`) and only promotes the built candidate to `azerothcore-admin:local` — the tag the installed systemd unit and future `docker compose` recreation actually use — after the candidate's health check and full verifier both succeed. Don't add a step that promotes earlier or skips the lock. Redeploy runs `sudo mkdir -p`/`chown` on `azerothcore-admin/data` **only when it is missing or not owned by the caller** (`stat -c %u:%g` vs `id`), so non-interactive callers such as the upgrade cutover never hit a password prompt; the admin installer still always uses sudo.

**Backup labels, pruning, and failure.** Labels: `daily` (nightly cron), `manual`, `prerestore` (in-app Restore's safety archive), `preclear` (Clear bots), `preupgrade` (cutover's cold backup), `prerollback` (an upgrade rollback's copy of the upgraded state). Stop/Restart/Apply take no backup. Pruning is 7 days, owned by `backup.sh` daily mode: it deletes archives of every label **except `preupgrade` and `prerollback`** plus old legacy artifacts. Those two are never pruned (rollback points / the way back to the upgraded state) — delete them by hand once no longer needed. The admin regex in `backups.py`, the `.badge-<label>` CSS and `cloud_config.ALL_LABELS` (which also has `imported`, the label of an Import & Restore upload) must list every label. A missing DB or a bad dump is never a successful backup: `backup.sh` probes all four DBs first, then validates the single dump (four canonical `-- Current Database` sections in order, `-- Dump completed` footer); any failure exits non-zero without publishing an archive or pruning, leaving existing archives untouched. v2 writes no `-partial-` archive, and both restore paths reject a manifest with `skipped_databases`.

**Cloud backup (Proton Drive) copies archives off the box through one allowlisted CLI door and one TPM-sealed vault.** Optional, driven from the Backups tab (issue #46; design in the local `docs/superpowers/specs/2026-10-28-admin-cloud-backup-design.md`). Files, all under `wow-server-sp-admin/`: `app/services/cloud_config.py` (settings/state/log stores, folder rules), `cloud_plan.py` (pure rules: filename stamps, candidates, retention, `is_backup_name`), `cloud_cli.py` (`ProtonDriveCli`, the only code that spawns `proton-drive`; fresh env, stdin `/dev/null`, per-call timeout), `cloud_vault.py` (`SessionVault`), `cloud_sync.py` (`run_sync`, one upload+retention pass), `cloud_backup.py` (`CloudService`/`get_service()`: the cloud lock, sign-in, loop, status), `app/templates/partials/cloud_panel.html` (routes `/api/cloud/*` always answer 200 with the re-rendered panel), `scripts/tpm-env.sh`. It adds no `/ac` mount and never touches `backup.sh` or the AC stack. One `threading.Lock` (the cloud lock) serialises every CLI and vault operation — the CLI's sqlite cache and the `pass` entry are not multi-process safe; requests that find it held get `CloudBusy` (never wait), it is independent of the action runner and of `.backup.lock`, and a sign-in holds it up to 11 min (its URL/process live only in memory, so a restart never looks "waiting"). A run, a folder check and Create folder use the folder they read at their start for every CLI call (a run's uploads and trashes too), so `save_settings` refuses a **folder change** with `CloudBusy` and saves nothing while one of them holds the lock (they read the folder under `_state_mu` after taking it, so the check cannot race them); a same-folder save (e.g. retention) still goes through, and so does a folder change during a pending sign-in (it only runs a read-only `fs info`, whose result `_update_state(folder=…)` drops once the folder changed). State-changing `/api/cloud/*` routes call the service through `main._await_thread_completion`; only the panel read uses a bare `asyncio.to_thread`.

**Cloud backup — CLI allowlist and confinement (do not widen).** `ProtonDriveCli` can express only `auth login --json`, `auth logout`, `version`, `fs info|list --json <folder>`, `fs upload --json -f skip -t <archive> <folder>`, `fs trash --json <folder>/<name>` and `fs create-folder --json <parent> <leaf>`; `_check_allowed` rejects any other first two argv words, so download/delete/empty-trash/move/rename/sharing do not exist in code (`tests/test_cloud_cli.py` asserts every argv shape against `tests/fake_proton_drive.py`). Its environment is built from scratch (`PROTON_DRIVE_CREDENTIALS_STORE=pass`, cache/`GNUPGHOME`/`PASSWORD_STORE_DIR` under `secrets/`, `TPM2TOOLS_TCTI=device:/dev/tpmrm0`, nothing inherited from the app). Confinement: the folder setting must be `/my-files/…` or `/shared-with-me/…` plus at least one more segment (`normalize_folder`, checked on save and before every run); a segment shaped like a node UID (`<22 or 88–108 chars>~<…>`) is refused because the CLI would resolve it as a UID and leave the folder; a name to trash must pass `is_backup_name` (backup regex, no `/`, `\`, `..`, control characters) and be a `type == "file"` entry of the folder's own listing; an upload path must equal what `backups.resolve_backup_archive` returns; upload is always `-f skip -t`, so a Drive file is never replaced; `create-folder` makes only the last segment, only from the explicit button, and refuses a leaf starting with `-`.

**Cloud backup — run rules.** The loop wakes every 10 min, but a wake-up is a local check (`CloudService.due`): Proton is contacted only when a candidate is missing from the last stored listing (`state.json` `remote`), or on **Upload now**; candidates are the archives of the selected labels within `retention_days`, plus selected `preupgrade`/`prerollback` archives at any age (`select_candidates`), so an old rollback point is still uploaded. After a `partial`/`error` run the next automatic attempt waits 60 min (`next_auto_attempt`; Upload now ignores it); nothing runs automatically while a sign-in is pending. A run (`run_sync`): `fs info` → `fs list` → upload each missing candidate newest first → re-list and judge by the listing alone (present = same name and SHA-1, or same size when the Drive reports no digest; **conflict** = same name, other content — reported in the panel, never replaced and never trashed to make room; failed = upload or local read error) → **retention only when the newest candidate is confirmed in the Drive** (an older stuck file does not block it) → every trash is confirmed by re-listing. Retention trashes plain-file backup names whose filename-stamp date is more than `retention_days` (default 7, 1–90) before today UTC (the cut-off of `backup.sh`'s `find -mtime +7`); never `preupgrade`/`prerollback`, never the newest remaining archive or anything sharing its date, never a name listed twice or whose stamp does not parse. It is **trash only** (`fs trash`, recoverable): the owner empties the Drive trash; the Drive applies its own rule rather than mirroring local deletions because a wiped server must not wipe the cloud copies. `stalled` = enabled, last result `partial`/`error`, and more than 26 h since the last success — or, when there never was one, since the first failure (`failing_since`); so a first failure is already stalled when the last success is over 26 h old. The panel and the card say "No fully successful cloud run for over a day" (one file that keeps failing makes every run `partial`, so it can show while new archives upload fine). The badges and the card's "N in Drive" leave out names with a `conflict` issue (`status().in_drive`), though `remote` and `due()` still count them, so a known conflict does not start a run every wake-up. `state.json` writes are advisory: when one fails, `CloudService` keeps the newest state in memory (`_load_state`) so `status()`, `due()` (back-off, listing) and later updates use it, and the panel shows "Could not save the cloud status file — check that the admin data folder is writable." until a write succeeds; a restart loses that memory. Run results: `ok`, `warning` (conflicts only), `partial`, `error`; connection: `disconnected`, `connected`, `vault_error`.

**Cloud backup — vault (`data/cloud/secrets/`, mode 700, never in backup archives).** `gnupg/` (`GNUPGHOME`, with `gpg-agent.conf`), `store/` (the `pass` store holding the CLI session), `passphrase.jwe` (the GPG passphrase sealed with `clevis encrypt tpm2 '{}'`, **no PCR policy**: kernel/firmware updates do not break it, it binds to this TPM chip only), `keygrips`, `cli/` (CLI cache/app data/logs). The passphrase is random, reaches clevis/gpg over stdin only and exists nowhere else; the app never reads the session, no route returns it and CLI text that names a session field is replaced (`_scrub`). gpg-agent holds the passphrase only during an `unlocked()` block (`allow-preset-passphrase`; cache TTLs 86400 in `gpg-agent.conf` because the agent is killed at the end of every unlock, which is what forgets the key); the killed agents are reparented to PID 1, hence `init: true` in `docker-compose.yml` (uvicorn would leave zombies). Agent sockets live in `GNUPGHOME`, so keep that path under the 108-byte UNIX-socket limit. Only **Connect** creates a vault, or recreates it when the sealed passphrase no longer unseals (TPM cleared); an unlock failure during a run or folder check only sets `vault_error` ("reconnect"). **Disconnect** is the only other thing that deletes `secrets/`: `auth logout`, then delete, keep `config.json`; it also works when the vault cannot be unsealed. **`auth logout` does not revoke the session at Proton** — it only deletes the CLI's local copy — so Disconnect and `uninstall-azerothcore-admin.sh` (which prints the reminder, also in `--dry-run`) tell the owner to revoke it in the Proton account's session list. Until revoked the stored session can read, change and trash the whole Drive (and probably more of the account's encrypted data) but cannot change the password, 2FA or recovery settings; anyone controlling the running server or the admin container (which has the Docker socket) can use it, and the admin has no login, like every other page.

**Cloud backup — TPM mapping, "no TPM → unavailable", verifier.** `docker-compose.yml` maps `${TPM_DEVICE:-/dev/null}:/dev/tpmrm0` and adds `${TSS_GID:-1000}` to `group_add` (host `/dev/tpmrm0` is `tss:tss 0660`). `scripts/tpm-env.sh` (sourced by the installer and the redeploy; functions only) has `resolve_tpm_env` (`TPM_DEVICE` = `/dev/tpmrm0` if it is a character device, else `/dev/null`; `TSS_GID` = the `tss` group's GID, else `HOST_GID`, else `id -g`) and `backfill_tpm_env`, which **appends** whichever of the two keys the admin `.env` lacks and never edits an existing line — a deliberate exception to "redeploy preserves `.env`", because re-running the installer on a live admin trips its own port check. Mapping `/dev/null` keeps one compose file valid everywhere; whether a TPM really works is decided only by `SessionVault.tpm_available()` (clevis seals and unseals a random probe; run at startup by `CloudService.probe`, which also reports a missing `proton-drive` binary, and again by the loop's `tick` about hourly (`REPROBE_SECONDS`) while it is unavailable for any reason but the missing binary, so a TPM that failed once at start-up comes back without a restart). No working TPM means **unavailable by design**: the panel says "Not available" with the reason ("Could not use this server's TPM security chip…") and Connect and the settings form are hidden — there is no software-only fallback; Disconnect stays offered there while a vault is on disk (`status().has_stored_session`, file checks only) or the connection is not `disconnected`, because it works without unsealing. `verify-azerothcore-admin.sh` step 8b prints one `[INFO] cloud backup: …` line (`off` / `connected, last success <N>m|h|d ago (<ISO>)|never|unknown[, last result <r>]` — minutes under 1 h, hours up to 48 h, then days; `unknown` for a stamp of the right shape that is not a real time / `<connection>, last result <r|none>` / `status unreadable (<reason>)`) from `data/cloud/{config,state}.json`, using only `enabled`, `connection`, `last_result`, `last_success`, each checked against a fixed shape. It is INFO-only on purpose: an outage at Proton must not fail the verifier, because the admin redeploy rolls back when it fails. Rolling back the admin (or an AC upgrade `rollback` before `finalize`, which restores the pre-cutover admin image) removes the panel until the next admin redeploy; `data/cloud/` is untouched.

**Cloud backup — pinned CLI and live acceptance.** The Dockerfile installs `proton-drive` from `https://proton.me/download/drive/cli/${PROTON_DRIVE_CLI_VERSION}/linux-x64/proton-drive` (currently 0.9.0) and checks it with `sha512sum -c` against `PROTON_DRIVE_CLI_SHA512`; a mismatch fails the build. To bump it, edit **both** `ARG`s from the linux-x64 entry of `https://proton.me/download/drive/cli/version.json`, rebuild, then re-check the CLI's real `--json` output against the canned shapes in `tests/test_cloud_cli.py` (served by `tests/fake_proton_drive.py`): the CLI is pre-1.0, the parsers fail closed as a `parse` error, and the INFO-only verifier line cannot catch a wrong parser. The unit tests never talk to Proton, so the first admin redeploy that ships this needs the owner-run acceptance from the spec (connect from the Backups tab, set a dedicated Drive folder, Upload now, confirm in Proton that the archives arrived and show "In Drive", and that a second Upload now uploads nothing, then compare a read-only `fs list`/`fs info` with the fixtures).

**Armory (`/armory`, `/armory/<guid>`; design in the local `docs/superpowers/specs/2026-10-29-admin-armory-design.md`) shows one character's saved gear, talents, glyphs and stats, plus a 3D model drawn by Wowhead's viewer through an allow-listed caching proxy.** Files under `wow-server-sp-admin/`: `app/services/armory.py` (the DB reads and the pure page/model rules), `dbc.py` (WDBC reader, `DbcStore`), `wow_reference.py` (static tables), `armory_assets.py` (the proxy), `armory_resolver.py` (display IDs), `app/static/armory.js`, `templates/armory.html` + `partials/armory_*.html`. Read-only toward AC: every query is a `SELECT`, at most 8 per character view — the page 6 (header, equipment, average item level with the Players ranking's expression, talents, glyphs, stats) and the model API `GET /api/armory/<guid>/model` 2 (header and equipment only, `collect_model_inputs`) — no console command, no attach, no new mount under `/ac`. Players-page names (Online now, All characters, both rankings) link to `/armory/<guid>` with no visible change (`.char-link`). `/armory/assets/*` and the model API run on the armory's own `anyio.CapacityLimiter` (8 tokens), so a slow Wowhead cannot take the default thread pool; the model API resolves items with ≤ 4 workers.

**Armory — `armory_assets.py` is the feature's only door to the internet (do not widen).** Hosts `wow.zamimg.com` and `www.wowhead.com` only. `resolve_upstream` maps exactly these local paths (regex on the whole path, `<n>` = `[0-9]{1,8}`) to `https://wow.zamimg.com/modelviewer/<same path>`: `live/viewer/viewer.min.js`, `wrath/meta/{character,charactercustomization}/<1–22>.json`, `wrath/meta/armor/<1|3|4|5|6|7|8|9|10|16|19|20>/<n>.json`, `wrath/meta/{item,itemvisual}/<n>.json`, `wrath/m2/<n>.m2`, `wrath/skin/<n>.skin`, `wrath/textures/<n>.webp`; and `icons/<[a-z0-9_-]{1,64}>.jpg` to `https://wow.zamimg.com/images/wow/icons/large/`. Anything else is a 404 without an upstream call. The item-XML door (`https://www.wowhead.com/wotlk/item=<entry>&xml`, `item_xml_url` / `fetch_item_xml`) is internal only: no route reaches it, only the display-ID resolver, and its answer is never cached. `fetch_upstream` re-checks every URL against the allow-list and builds its opener from scratch (no environment proxy, no cookies, redirects are errors, `User-Agent: wow-server-sp-admin/1.0`, `Accept-Encoding: identity`, no Referer/Origin), 20 s budget, 16 MB cap, never a retry; content types come from our extension table. `AssetProxy`: ≤ 4 upstream fetches at once (waiting longer than the fetch timeout + 5 s for a slot = 503, no cool-down), single-flight per path, a 60 s per-host cool-down after a network error, 429 or 5xx (misses answer 503, hits still serve; the footer shows "Wowhead unreachable since …"), a 1 h negative cache for upstream 404s. **No prefetch**: nothing is fetched that a page view did not ask for. Cache `data/armory/cache/<local path>` (0600 files, 0700 dirs, tmp+rename, served `immutable`), cap 300 MB: after a write over the cap the least-recently-hit files (a hit = `utime`) go until under 80 %, never `live/viewer/*`; an unwritable cache serves pass-through and the footer says why. `AssetProxy`/`AssetCache`/the resolver are single long-lived instances (`get_proxy()`, `get_resolver()`; the cache keeps a running byte total), and `status()`/`size_bytes()` take the cache lock — call them off the event loop.

**Armory — viewer script pinned by hand; the On/Off switch; nothing in backups.** `live/viewer/viewer.min.js` is fetched on first use with `viewer.meta.json` (`etag`, `last_modified`, `fetched_at`, `sha256`, `size`) and never re-fetched implicitly; the footer's **Update** does a conditional GET and keeps the previous copy (`*.prev`) for **Revert**; Update refuses while the 3D viewer is Off. It is served `no-cache` with its sha256 as ETag. **Clear** deletes every cached asset and the negative cache but keeps `live/viewer/*` (else the next view would silently pin whatever upstream serves that day). **3D viewer On/Off** (`data/armory/armory.json`, `{"enabled": bool}`; missing or unreadable = On) stops all upstream traffic when Off: misses answer 503 and the resolver records nothing, cache hits still serve. The repo never contains `viewer.min.js` or any Blizzard/Wowhead asset. `data/armory/` is not in backup archives (`backup.sh` archives only `maintenance.json`/`presence.json`): all of it is re-fetchable, which the admin uninstaller says.

**Armory — model facts (measured by the 2026-10-29 spike; do not re-derive).** Viewer config: `contentPath = /armory/assets/wrath/`, `hd: true`, `type: 2`, `models: {id: modelId, type: 16}`; `modelId = race*2 - 1 + gender` with the DB gender as-is (0 male, 1 female). Customisation options are mapped server-side (`map_customization`, `OPTION_NAME_MAP`) by option **name**, never by position (`Options[]` order differs per race; "Horn Style" is the Tauren's hair style, everyone else's facial feature); the model API returns ready `[{optionId, choiceId}]` and logs an unknown name once — a race that renders a wrong face or hair gets one more table line. Items: viewer slot = `item_template.InventoryType`; neck, rings and trinkets are never sent; the off hand goes as 14 shield / 23 held / else 22; the viewer folds 13/17/21/25/26 onto its main-hand key and 14/15/22/23 onto its off-hand key, so the ranged slot is sent only when that key is free (a bow only with no off-hand item, thrown/gun/crossbow/wand only with no main-hand item), a relic (28) never; a robe (20) stays 20. Wowhead regenerated its Wrath model data, so some 3.3.5 `displayid`s no longer exist there (8 of 37 in the spike): `armory_resolver.py` probes the DB id's meta file, on a 404 asks the item XML for the current id and verifies its meta, and records `entry → id` in `data/armory/displayid-map.json` (a found id is permanent; `null` = a definitive miss, asked again after 7 days; a transient failure records nothing). The model API's `unresolved` lists definitive misses (the slot's "no 3D" mark), `pending` the transient ones.

**Armory — CSP: no eval, one hashed inline script.** `main.ARMORY_CSP`, added by the pure-ASGI `_ArmoryCSP` (outermost, so gzip'd and error answers too) to `/armory` and `/armory/*` only, never `/api/armory/*`: `default-src 'self'; script-src 'self' 'sha256-…'; style-src 'self' 'unsafe-inline'; img-src 'self' blob:` (the reason for each source is in its comment). It is what turns "the browser never talks to Wowhead" into a guarantee, also for the viewer's protocol-relative `viewer.css` link (which `armory.js` drops from the HTML jQuery parses). The hash is of `base.html`'s only inline `<script>` (toast / nav pill): editing that script requires updating the hash — `test_csp_script_hashes_are_exactly_the_pages_inline_scripts` fails and prints the new value. With no `'unsafe-inline'`/`'unsafe-eval'` for scripts, `base.html` and the armory templates must use no inline handlers (`onclick=` …), no `hx-on`, no `hx-trigger` filters (`[…]`), no `hx-vals` with `js:` (htmx evaluates those as code), and no Jinja interpolation inside `base.html`'s inline script (the hash would change per render). jQuery is required by the viewer (without it the script throws `jQuery is not defined` while loading; it uses `$.getJSON`, `$.ajaxTransport("+binary")`, `container.width()`); `armory.html` loads `/static/jquery.min.js` (`defer`, before `armory.js`) only on a character page — a vendor file like HTMX (see the vendor-files paragraph below).

**Armory — client data, stats setting, uninstall order, verifier.** The page reads 12 DBC files (`dbc.DBC_FILES`: Talent, TalentTab, Spell, SpellIcon, GlyphProperties, SpellItemEnchantment, GemProperties, ItemRandomProperties, ItemRandomSuffix, ItemSet, ItemDisplayInfo, RandPropPoints — the last for random-suffix stat amounts) from `$CLIENT_DATA_DIR/dbc`: AC's `azerothcore_ac-client-data` volume, joined as an **external** volume and mounted **ro** at `/client-data` (`docker-compose.yml`, `CLIENT_DATA_DIR: /client-data`; not under `/ac`). AC installer Phase 4 creates it; install and redeploy check `docker volume inspect azerothcore_ac-client-data` before building and stop with "install AzerothCore first". A lifespan daemon thread parses the files at start (else the first view does); a missing or unreadable file only degrades its table (ids instead of names, one footer line). The running admin holds the volume, so **uninstall the admin before AC**: otherwise the AC uninstaller's `docker volume rm` of it fails (recorded as a cleanup failure). The Stats tab reads `character_stats`, which AC writes only with `PlayerSave.Stats.MinLevel` ≥ 1 (default 0 = never; set it in Settings — the tab's note shows the current value); keep `PlayerSave.Stats.SaveOnlyOnLogout = 1` (the default), so it is one row per logout inside the existing save, not one on every periodic save. `verify-azerothcore-admin.sh` step 8c prints one `[INFO] armory: dbc <ok|missing: A,B|unknown (admin container not running)>, cache <N> MB, viewer <fetched <ISO>|fetched (date unknown)|not fetched>, 3d <on|off>` line: a read-only `docker exec azerothcore-admin test -r /client-data/dbc/<file>` per name (its `armory_dbc_files` list must equal `DBC_FILES`; a test compares them), `du -sm data/armory/cache`, and fixed-shape reads of `armory.json`/`viewer.meta.json`. INFO-only, like 8b: an outage at Wowhead must not fail a verify, because the admin redeploy rolls back when it fails.

**Restore refuses other source revisions.** A dump restores safely only onto binaries built from the revisions that wrote it (newer ones re-run migrations against it, older ones cannot read a migrated schema). Host `restore-azerothcore.sh` compares the manifest's `git_revisions` (core + 3 modules) with each checkout's `HEAD` before anything is stopped or dropped. A checkout with no `.git` of its own (git would walk up to a parent repo) or a failing lookup counts as `unknown`, and `unknown` on either side fails closed. `--allow-version-mismatch` overrides it with a WARNING; for fresh-machine DR, check out the archive's revisions and rebuild first, or pass the flag knowingly. In-app restore (`actions.revision_mismatch` / `current_stack_revisions`) applies the same rule with no override: cross-version restores are host-only. The core/module dir mapping is duplicated in `restore-azerothcore.sh` (`dirs`), `actions.py` (`REVISION_DIRS`) and `backup.sh` (`git_rev` calls) — keep them in sync. The host restore also writes back `config/etc/*.conf` and `config/admin-data/*`.

**`scripts/restore-drill.sh ARCHIVE [--compare-live]` proves an archive restores without touching the live stack.** It streams the archive's SQL over stdin into a throwaway `acup-drill-db` MySQL container (resource-capped; `--network none` or an `--internal` network; no published ports or bind mounts — it fails closed and removes the container if `docker inspect` shows otherwise; names must start with `acup-`), then checks the table inventory against the dump's own `CREATE TABLE` counts, the `-- Dump completed` footer on every SQL member, and that key tables are non-empty. `--compare-live` also reads exact `COUNT(*)`s from `ac-database` through a `READ ONLY` session using identifier-filtered table names; differences are advisory and a table absent live is reported `live=missing`. The container (and, in `--keep` rehearsal mode, its password file) is removed on every exit path except a passed `--keep` run. It starts a container on the host daemon, so run it only when the user asks (see the live-stack safety rules); tests drive it with a stub-only `PATH`.

**Never pipe `docker logs` (or a captured log) into `grep -q` under `pipefail`.** `grep -q` exits at the first match, the writer dies of SIGPIPE (141) once the log is long, and `pipefail` turns a real match into "no match" — readiness waits, the playerbots fatal-log check and the startup binding-log lookup all had this. Use `grep -q … < <(docker logs …)` or a here-string (`grep -qF … <<<"$log_content"`). `test_lifecycle_shell_behavior.py` has a static test over `scripts/*.sh` plus long-log tests whose docker stub `exec`s `cat`, so the stub itself takes the SIGPIPE as real `docker logs` does.

**Restore validates before it becomes destructive.** Both restore paths preflight every selected SQL dump (present, non-empty, completed) before stopping the server or dropping a database. For in-app restore, an import failure after the `prerestore` safety archive leaves the server stopped and reports that archive; do not auto-restore or restart into an uncertain state.

**`_await_thread_completion` (`app/main.py`) is the shield-and-wait pattern for any cancellable mutation on a worker thread** — `asyncio.shield`s the `to_thread` task, and on caller cancellation still awaits the underlying thread before re-raising, so cleanup/lock-release can't run while the thread is still mutating. Used by both import-restore staging/validation and progression-apply; reuse it for any new cancellable destructive route instead of a bare `asyncio.to_thread`.

**`resolve_backup_archive` (`app/services/backups.py`) is the one non-symlink-following archive-path resolver** — lexical check → `lstat` → reject symlink/non-regular → resolved-parent containment. Listing, download, and `run_restore` all use it (the worker re-checks itself rather than trusting the route). Any new route that turns a client-supplied archive name into a path must go through this, not a fresh `is_file()`/string check.

**`MaintenanceScheduler` is an asyncio background task, not cron.** Started in `lifespan` (`main.py`) on `app.state.maintenance_scheduler`, cancelled on shutdown. Polls every 30 s but fires only when `now.minute == 0` (top of the UTC hour). Same-hour jobs run sequentially so they do not collide with the action runner; externally busy actions are logged as skipped for that hour. `ADMIN_DATA_DIR` (default `/admin-data`, from `azerothcore-admin/data/`) holds `maintenance.json` (config) and `maintenance-log.jsonl` (last 20 runs, trimmed on append); maintenance-log/config write errors are advisory and must not kill the scheduler.

**`PresenceAnnouncer` (`app/services/presence.py`) tracks per-account `characters.online` presence always; announcing is gated by the toggle.** Asyncio task started in `lifespan` on `app.state.presence_announcer`, polling every 15 s (`POLL_INTERVAL_SECONDS`) whenever `ac-worldserver` is running. `presence.json`'s `announce_enabled` (Maintenance page → Player Announcements) only decides whether transitions are sent over the console; the tracker keeps observing when it is off so the Players page / dashboard card (`tracker.snapshot()`, guarded by a `threading.Lock` — `tick` runs on a worker thread, routes read from the event loop) still name the human character. Enabling announcements never announces sessions already known to the tracker. AC writes `characters.online=1` synchronously at character login (`CharacterHandler.cpp`), and with the local logout patch (see *Pinned upstream + upgrades*) logout marks only that character offline (`OnPlayerCanMarkAccountOffline` runs the per-character `UPDATE characters SET online = 0 …` and returns false, so core `3f2969dd` `WorldSession.cpp` skips `CHAR_UPD_ACCOUNT_ONLINE`), so the flag is immediate. Without the patch the core marks the **whole account's** characters offline at any logout (upstream behaviour) — an alt-bot dismissal would flag the human offline for up to 15 min — so Check 24 failing on the patch is a presence regression, not cosmetic. `latency`, by contrast, is only written on `PlayerSave.Interval` (the Players page now uses the tracker too — see above). `PresenceTracker` is per **account**: login = 0 → ≥1 online chars (the first char is the human — alt-bots can only be summoned by a logged-in master, so they never cross the boundary; two chars in one poll → account name), logout = two consecutive absent polls (a quick character swap is silent). `acore_auth.account.online` is **still not used** — it was unusable because alt-bot (headless) session teardown ran `UPDATE account SET online=0` for the human's account (`WorldSession.cpp:~188`); the pinned core no longer clears it for headless sessions, but nothing relies on that. The tick skips while `runner.current()` is set (an action may own the console), and `reset()`s (silent reseed) when `ac-worldserver` isn't `running` and whenever its `StartedAt` changes — so Stop/Restart/boots never produce a burst. Console/DB failures are logged and dropped, never retried.

**`mark_attempted` is called before `runner.start`.** A job's `last_runs` stamp is committed before `runner.start`. If start raises (e.g. another action running), the job logs "skipped" but the stamp stands — no retry until the next UTC hour. Prevents double-fire when the scheduler ticks twice in the same minute.

**Midnight-crossing stop/start windows are unsupported.** `MaintenanceStore.validate` requires `window_start_hour_utc > window_stop_hour_utc` (strictly); "stop 23:00, start 02:00" is rejected 400. Both are 0–23; no cross-day arithmetic.

**Expected admin test warnings.** Dockerized pytest may print pip's "running as root" + new-version notices (disposable container) and one Starlette `multipart` pending-deprecation warning. The application uses `python-multipart==0.0.31`; the warning remains in the Starlette version resolved by `fastapi==0.115.0`. Upgrade FastAPI and Starlette together, then rerun the admin and browser suites; do not suppress the warning or downgrade the multipart dependency merely to hide it.

**Header branding (Customization tab, issue #45) is read on every page render.** `base.html` calls the Jinja global `branding()` (`app/services/customization.py`, `CustomizationStore.branding()`) for the header name, the 36px logo (`/customization/logo?v=<sha256[:12]>`, served with its detected type and `nosniff`) and the favicon. Routes pass `title` as the **page name only** (`"Players"`, `None` on the dashboard); `base.html` renders `<name> · <title>`, so don't put the app name back into route titles. The logo type comes from the file's magic bytes (PNG/JPEG/GIF/WebP only; never SVG, never the upload's name or Content-Type), ≤ 512 KB; the name is trimmed, ≤ 32 characters, no `Cc`/`Zl`/`Zp`. `save()` validates everything before writing anything; `config.json` and `logo.<ext>` are regular files (tmp+rename), unreadable settings fall back to defaults. `post_customization` reads `request.form()` by hand because an empty file input can arrive as a plain `""` field. Not in backup archives (`backup.sh` archives only `maintenance.json`/`presence.json`). The header is `--nav-h` tall (60px); use that token, not a literal, in any `calc(100vh - …)`.

**The top nav bar lives in `base.html`, not `dashboard.html`.** `#last-refresh` and `#nav-status-pill` are `<span>`s in `<nav class="topnav">`. The pill polls `/api/status` every 60 s via `hx-get`/`hx-swap="none"` + an `htmx:afterRequest` handler that updates its text/class — **not** `outerHTML`/`hx-select` (which would destroy the polling element after one swap). The `htmx:afterSwap` listener updates `#last-refresh` only when the dashboard `#status` card swaps (dashboard only; the pill polls independently on every page).

**`switchLog()` is in `dashboard.html`'s inline `<script>`, not `settings.js`** (which only loads on the settings page). `partials/logs.html`'s `onclick="switchLog(...)"` needs it on the dashboard too — don't move it.

**`settings.js` source-file checkbox selector is `.check-group input[type=checkbox][value]`.** New sidebar checkboxes that should trigger a re-render must live inside `.check-group` (or be wired separately). The sidebar class changed from `.settings-filters` to `.settings-sidebar`/`.check-group`.

**Settings page defaults to "Show only modified."** The `only-modified` checkbox is `checked` in `settings.html`, so `_render()` first paints with `modifiedOnly = true` (only `source === 'admin'|'installer'` keys). No "Show all" toggle, no `COMMON_KEYS`; unchecking shows the full ~1996-key index. With the filter on and no modified keys, it renders one `.empty-state` paragraph — not a bug on a fresh install. The pending badge and Apply button update before the empty-state early return, so they always reflect true pending state.

**SSE activity log needs the canonical htmx-ext-sse pattern — `sse-connect` on a parent, `sse-swap` on the child.** `registerSSE()` finds the EventSource via `getClosestMatch(elt, hasEventSource)`, an ancestor walk; same-element use happens to work but is fragile and unsupported. In `dashboard.html`: `.panel-body` has `hx-ext="sse" sse-connect="/api/action/stream"`, and `#action-log` (`<ul>`) has `sse-swap="progress,done" hx-swap="beforeend"`.

**`GZipMiddleware` must not compress `/api/action/stream`.** Browsers send `Accept-Encoding: gzip` on every `EventSource` request; gzipped SSE makes some browsers silently drop all events (permanently empty activity log). `main.py` uses `_GZipExcludeSSE`, an ASGI wrapper that bypasses GZip for that path and delegates the rest. Don't replace it with a plain `GZipMiddleware`.

**`config_index.py` comment parsing has two rules.** `parse_dist_file()`: (1) *per-key blocks* — `_comments_by_key()` keys a structured section by the SHORT identifier in the comment text (e.g. `"BotActiveAlone"`), not the full key, so `active_comment_by_key.get(key)` falls back to `key.rsplit(".",1)[1]` on a miss — keep that fallback (it's what lets `Playerbots.BotActiveAlone` find its description). (2) *flat blocks* — consecutive KV lines after a comment share it, but sharing stops at a blank line (`had_blank` clears `active_comment`), preventing descriptions bleeding across unrelated keys.

**`$STACK_DIR/build/dist/` is not in the repo** — the installer creates it (`install-azerothcore-admin.sh:192`). Any `rsync -a --delete "$REPO_DIR/" "$STACK_DIR/build/"` wipes it; always `mkdir -p "$STACK_DIR/build/dist"` right after the rsync, before `stage_conf_dists` copies the `.conf.dist` files in.

**Vendor files (`htmx.min.js`, `htmx-sse.js`, `jquery.min.js`) are ≤ 60-byte placeholders in the repo** — the install script fetches the real ones from unpkg (`htmx.org@2.0.3`, `htmx-ext-sse@2.2.2`, `jquery@3.7.1`, the Armory's; the Dockerfile copies them with `app/`); install and redeploy exclude all three from their `rsync -a --delete` into `build/`, and redeploy carries the installed copies into its candidate. Any new `rsync -a --delete` must exclude all three or the app serves broken HTMX (silently relying on the browser cache) or an Armory without its viewer. Redeploy aborts if any of them is ≤ 200 bytes and prints the fetch for it, e.g. `curl -sSfL -o "$STACK_DIR/build/app/static/jquery.min.js" "https://unpkg.com/jquery@3.7.1/dist/jquery.min.js"` — an install older than the Armory has no `jquery.min.js` yet, so run that once before its first redeploy (the vendor URLs are listed in both scripts; `tests/test_armory_deploy.py` keeps them equal).

**Mobile layout is `@media (max-width: 768px)` only — desktop untouched above it.** `#last-refresh` is hidden on mobile. The settings sidebar becomes a sticky bar with a collapsible `.mobile-collapsible` toggled by `#mobile-filter-toggle` (JS at the bottom of `settings.js`). The detail panel is a full-screen overlay (`position: fixed; translateX(100%)` → `.mobile-visible` removes it); `selectKey()` adds `mobile-visible` when `window.innerWidth <= 768`; `closeMobileDetail()` (global in `settings.js`) clears it and `state.selected` (Back button calls it). `#result-count` must stay OUTSIDE `.mobile-collapsible` so the count shows when filters collapse.

## Constraints to preserve

- Scripts must **not** run as root — the `EUID -eq 0` guard in `install-azerothcore.sh` (and `install-azerothcore-admin.sh`) is intentional; scripts call `sudo` internally.
- Password inputs accept only shell-safe chars (`letters, numbers, . _ @ % + = , : -`) so the config file is safe to `source` on resume.
- Neither uninstaller (`uninstall-azerothcore.sh`, `uninstall-azerothcore-admin.sh`) may use `--remove-orphans` (would remove unrelated containers sharing the Compose project name); the admin's `docker rm -f azerothcore-admin` covers its single service.
- `verify-azerothcore.sh` / `verify-azerothcore-admin.sh` stay on `set -u` without `-e` so all checks run regardless of individual failures.
- The admin app must edit nothing under `/opt/stacks/azerothcore/` except `docker-compose.admin.yml` and `backups/*` — the `/ac/` mount is ro to enforce this; add no other rw sub-mount.
- `scripts/uninstall-azerothcore.sh`'s `STACK_DIR`/`STATE_FILE`/`CONFIG_FILE`/`SYSTEMD_UNIT` are immutable `readonly` constants — no environment-override seam. Every removal (including the stack directory itself) passes through `safe_remove_literal`'s exact-match guard; `sudo` only changes *how* an already-approved literal is removed, never *which* path. Tests isolate by copying the script and rewriting these `readonly` lines (see `test_uninstaller_script.py`/`test_lifecycle_shell_behavior.py`), never by passing env overrides.
